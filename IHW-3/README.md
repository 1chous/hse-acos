Многопроцессная имитационная модель группы лифтов для **Linux**.
Диспетчер, каждый лифт и каждый пассажир — отдельные процессы.
Диспетчер хранит состояние модели, назначает вызовы и принимает события.
Участники выполняют команды асинхронно и согласуют обмен семафорами POSIX.

## Сборка

Все команды ниже выполняются из каталога `IHW-3`.

```bash
make
```

Из общих исходников собираются **четыре реализации и шесть исполняемых файлов**:

| Реализация | Исполняемые файлы | Запуск и взаимодействие |
|---|---|---|
| 1 | `build/elevator-unnamed` | родитель создаёт детей; общая память POSIX и неименованные семафоры |
| 2 | `build/elevator-named` | родитель создаёт детей; общая память POSIX и именованные семафоры |
| 3 | `build/elevator-server`, `build/elevator-client` | независимые процессы; общая память POSIX и именованные семафоры |
| 4 | `build/elevator-mq-server`, `build/elevator-mq-client` | независимые процессы; очереди сообщений POSIX и именованные семафоры |

Требуются компилятор C11, `make`, libc и API POSIX. Для тестового скрипта
нужен Python 3. Флаги `-pthread -lrt` обеспечивают сборку с используемыми
системными библиотеками; пользовательские потоки в программе не создаются.

`NAMED_SEMAPHORES`, `INDEPENDENT`, `CLIENT` и `MESSAGE_QUEUES` выбирают
вариант при компиляции. Все реализации остаются доступными одновременно.

## Входные данные

Обязательный аргумент — путь к текстовому файлу. В файле только
неотрицательные целые числа, разделённые пробелами или переносами строк.
Комментарии и лишние значения не допускаются.

```text
floors lifts capacity passengers seed strategy
arrival_min arrival_max travel_ms door_ms board_ms leave_ms
начальные этажи всех лифтов
from to для каждого пассажира
```

| Поля | Значение |
|---|---|
| `floors`, `lifts`, `capacity` | число этажей, лифтов и вместимость каждой кабины |
| `passengers` | число пассажиров, каждому соответствует отдельный процесс |
| `seed` | начальное значение генератора интервалов появления |
| `strategy` | `0` — старейший вызов и ближайший свободный лифт; `1` — ближайшая пара «свободный лифт — пассажир» |
| `arrival_min`, `arrival_max` | диапазон интервала между появлениями пассажиров, в миллисекундах |
| `travel_ms` | время движения между соседними этажами |
| `door_ms` | время открытия и отдельно время закрытия дверей |
| `board_ms`, `leave_ms` | время посадки и высадки одного человека |
| начальные этажи | ровно `lifts` значений |
| `from`, `to` | этажи отправления и назначения; ровно `passengers` пар |

Этажей должно быть не меньше двух, лифтов и мест — не меньше одного.
Пассажиров может быть ноль. Все этажи находятся в диапазоне `1..floors`,
этаж отправления отличается от назначения. Нижняя граница интервала
появления не больше верхней. Нулевая длительность разрешена.
Значения должны помещаться в `int`; число участников и размеры выделяемых
областей проверяются на переполнение. Фактическое число процессов и
объектов IPC также ограничено ресурсами Linux.

Например, `basic.in`:

```text
5 2 2 4 42 0
50 100 150 100 50 50
1 5
1 5
5 1
2 4
4 2
```

Два лифта вместимостью два человека начинают на этажах 1 и 5.
Четыре пассажира едут по маршрутам `1→5`, `5→1`, `2→4`, `4→2`.
Первый пассажир появляется после первого случайного интервала,
следующие — после последовательно накопленных интервалов.

Лифту назначается группа уже ожидающих пассажиров с одного этажа и
одного направления, не больше вместимости. Новые попутные вызовы в
текущий рейс не добавляются. После посадки лифт высаживает пассажиров
по пути в заданном направлении, затем получает новое назначение.
Оставшиеся без места вызовы сохраняются в ожидании.

## Запуск первых двух реализаций

```bash
./build/elevator-unnamed basic.in unnamed.log
./build/elevator-named basic.in named.log
```

В обоих случаях диспетчер создаёт `lifts + passengers` дочерних процессов
через `fork`. Включая диспетчера, работает `1 + lifts + passengers` процессов.
Если путь журнала не указан, используется `elevator-03.log`.

## Независимый запуск: общая память

Сначала запустите диспетчер в фоне:

```bash
./build/elevator-server basic.in demo independent.log &
server_pid=$!
```

**Дождитесь строки «Готово: сеанс demo; запустите участников 1..6».**
Затем запустите отдельные процессы участников:

```bash
for actor in 1 2 3 4 5 6; do
    ./build/elevator-client basic.in demo "$actor" &
done
wait "$server_pid"
echo $?
wait
```

Номера `1..lifts` принадлежат лифтам, остальные — пассажирам.
Для `basic.in` номера 1 и 2 — лифты, 3–6 — пассажиры 1–4.
Каждый процесс запускается отдельной командой; диспетчер их не создаёт.

`demo` — имя сеанса. У всех участников должны совпадать имя сеанса и
входные данные. Имя не должно быть пустым, содержать `/` или приводить
к переполнению буфера имени. Другой параллельный запуск получает другое имя.
Диспетчер ждёт всех участников и только затем отправляет `START`.

Первый `wait` ждёт диспетчер, `echo` выводит его код завершения,
последний `wait` дожидается остальных фоновых процессов.

## Независимый запуск: очереди сообщений

Порядок тот же. Сначала:

```bash
./build/elevator-mq-server basic.in demo_mq mq.log &
server_pid=$!
```

Дождитесь сообщения о готовности, затем:

```bash
for actor in 1 2 3 4 5 6; do
    ./build/elevator-mq-client basic.in demo_mq "$actor" &
done
wait "$server_pid"
echo $?
wait
```

В этой реализации `Session` — частная память каждого процесса.
Команды, события, регистрация и время старта передаются через очереди
POSIX. Именованные семафоры регулируют запись и чтение. Общая память
POSIX не создаётся. Ответ на регистрацию идёт в отдельную очередь по PID,
чтобы отказ повторному номеру не получил уже работающий участник.

## Что видно на экране и в журнале

Диспетчер печатает время от начала моделирования и события предметной
области: появление пассажира, регистрацию и назначение вызова, начало
движения, прибытие на этаж, операции с дверями, посадку, высадку и доставку.
Длительные действия выполняются процессами участников через `nanosleep`;
единого последовательного такта нет.

Журнал содержит те же строки событий и итог: число доставленных
пассажиров, среднее ожидание завершения посадки и число людей, по которым
оно посчитано. При остановке перечисляются недоставленные пассажиры и их
последние подтверждённые состояния. «Назначенный лифт 0» означает, что
лифт ещё не назначен.

`seed` воспроизводит последовательность входных интервалов при той же
реализации генератора libc. Порядок выполнения процессов и временные
отметки могут отличаться между запусками.

## Завершение и очистка

Штатное завершение происходит после доставки всех пассажиров и закрытия
дверей лифтов. Поддерживаются SIGINT и SIGTERM. В первых двух версиях
можно нажать Ctrl+C во время работы. Для фонового диспетчера:

```bash
kill -INT "$server_pid"
wait "$server_pid"
echo $?
wait
```

Для ручной проверки прерывания используйте медленный `interrupt.in`:
в нём один лифт и три пассажира, то есть участники `1..4`.
Автоматически этот сценарий проверяется командой `make check`.

Коды диспетчера: `0` — норма; `1` — ошибка данных или выполнения;
`2` — неверное число аргументов; `130` — SIGINT; `143` — SIGTERM.
При прерывании независимые участники могут завершаться с кодом `143`,
поскольку диспетчер останавливает их через SIGTERM.

Родитель ждёт детей через `waitpid`. В независимых версиях участники
подтверждают окончание роли сообщением `BYE`; ожидание при завершении
ограничено пятью секундами. После завершения закрываются отображения,
семафоры и очереди, удаляются созданные диспетчером имена.
После SIGKILL, аварии ядра или отключения питания такая очистка
не гарантируется: обработчик процесса в этих случаях не выполняется.

После окончания всех экземпляров можно проверить оставшиеся имена:

```bash
find /dev/shm -maxdepth 1 \( -name 'acos03_*' -o -name 'sem.acos03_*' \) -print
find /dev/mqueue -maxdepth 1 -name 'acos03_*' -print
```

```bash
make check
```

`test.py` выполняет **24 проверки**: шесть сценариев на каждой из четырёх
реализаций. Проверяются коды завершения, доставка каждого пассажира ровно
один раз на нужный этаж, вместимость, итог и журнал, SIGINT, завершение
участников и отсутствие имён IPC данного запуска. Есть таймауты ожидания.
Временные файлы создаются вне проекта.

Для строгой пересборки:

```bash
make -B check CFLAGS='-std=c11 -Wall -Wextra -Wpedantic -Werror -O2'
```

## Linux через Docker на macOS

Запустите Docker Desktop. **Из папки `IHW-3`, содержащей Makefile:**

```bash
docker run --rm -it --init -v "$PWD":/work -w /work gcc:14 bash
make check
```

Все процессы одного независимого сеанса должны работать в одном
контейнере: отдельный `docker run` по умолчанию создаёт другое окружение
IPC. Второй терминал можно открыть через `docker exec -it CONTAINER_ID bash`.
Внутри контейнера `/work` соответствует папке проекта на Mac.
